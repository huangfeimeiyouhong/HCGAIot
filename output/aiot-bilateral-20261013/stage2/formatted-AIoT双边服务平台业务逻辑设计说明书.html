第一章　平台定位与业务模型

1.1　定位转变

平台从原有的「物联网设备接口聚合 + 统一展现层」，转型为厨具厂家与物联网设备厂家共同入驻、供双方及客户端共同使用的双边服务平台。

这次转型不是功能叠加，而是平台商业模式的根本变化：原平台是展示工具，解决的是「谁接入、谁看数据」；新平台是交易与履约基础设施，解决的是「谁入驻、设备卖给谁、出问题谁修、履约质量如何」。

维度原有逻辑新定位
平台角色数据展示通道交易与履约基础设施运营方
参与方设备厂商（单向接入）厨具厂家 + 物联网厂家 + 客户端（三方共治）
数据粒度设备总数、在线数（聚合数字）单台设备个体台账（SN 级）
设备归属无归属概念每台设备有明确的所有权与责任方
告警只读展示可处置，且是工单触发源
业务闭环无（看到即结束）报修 → 处置 → 验收 → 归档全链路
商业价值展示价值履约数据沉淀与 SLA 可量化

1.2　三方角色定义

平台运营方：平台的运营主体，负责入驻审核、租户管理、规则配置、工单仲裁与争议处理。自身不持有设备，不承担履约责任。

厂家端：分两类主体，均为设备供给方。

  • 厨具厂家：生产厨具本体（灶具、冷柜、洗消设备、排烟系统等），拥有设备台账、整机质保与售后责任。
  • 物联网设备厂家：生产传感器、采集模块、网关等物联网部件，提供数据采集能力与通讯协议支持。
关键认知：两类厂家是互补而非竞争关系。一台实际交付到食堂的冷柜，通常由厨具厂家的本体加上物联网厂家的温度传感器与网关组成。这种物理构成决定了平台必须支持「一台设备由多个厂家的部件构成」的场景。

客户端：设备的最终使用与持有方，典型形态为学校食堂、酒店餐饮、团餐公司、经销商与运营商。客户端是服务的发起方与验收方。

1.3　核心业务对象与关系

平台的核心业务对象分为七类，其中绑定关系是整个模型的枢纽。

对象说明关键属性
租户 Tenant平台的数据隔离基本单位，厂家与客户各自独立成租户租户类型、审核状态、有效期
厂家 Vendor入驻平台的供给方主体厂家类型、资质、服务范围
产品型号 ProductModel厂家定义的产品规格，同型号对应多台实例型号编码、品类、参数、质保期
设备实例 Device一台物理设备，对应唯一 SNSN、型号、所有权、当前绑定客户
部件 Component物联网厂家提供的硬件，附着于设备之上部件 SN、固件版本、采集指标集
绑定关系 Binding装配绑定 + 产权绑定（详见 2.4）绑定类型、生效时间、失效时间
工单 WorkOrder客户发起的服务请求，是履约的载体状态、优先级、SLA 时限、关联设备与告警

1.4　设备聚合视角

平台在数据组织上引入「设备聚合视角」：客户端与平台视角看到的是一台完整设备（如「3 号冷柜」），而厂家视角看到的是自己供的那个部分（厨具厂家看这整台，物联网厂家看装在上面的温度传感器）。

这一视角差异是整个权限设计的出发点，详见第二章。

第二章　入驻与权限体系

2.1　租户模型

平台的所有业务数据均归属于某个租户，租户是数据隔离的第一道边界。

租户类型代码主体可见数据范围
厂家租户VENDOR厨具厂家、物联网厂家仅绑定到本厂设备的客户、设备、告警、工单
客户租户CUSTOMER食堂、酒店、团餐、经销商仅绑定到本租户的设备及其监控、告警、工单

平台自身持有全局视图，但财务、合同等敏感字段按需脱敏，所有运营操作留痕可审计。

2.2　厂家入驻审核流程

入驻不是注册即用，必须经过资质与能力双重审核。

状态状态码状态含义责任方可执行动作
待提交DRAFT已创建申请，资料未填完厂家编辑资料、提交审核
待初审PENDING_PRIMARY资料已提交，等待平台初审平台审核员通过初审、退回补充
待复审PENDING_SECONDARY初审通过，等待技术与商务复审平台技术 + 商务通过复审、退回补充、驳回
待整改RECTIFY复审未通过，需整改厂家提交整改材料
已驳回REJECTED审核不通过，流程终止—重新发起申请
试运营TRIAL审核通过，进入试运行观察期厂家接入设备、试运行
正式入驻ACTIVE试运行达标，正式开放—全量功能可用

流程流转规则：

  1. 厂家提交资料后进入「待初审」，进入该状态的申请锁定关键字段，不可再编辑。
  2. 初审通过进入「待复审」，平台在此阶段进行技术对接（协议适配、字段映射）与商务确认（服务范围、SLA 承诺）。
  3. 复审不通过分两种：资料类问题进入「待整改」，材料齐备后重新排队；能力类问题直接「已驳回」并记录驳回原因。
  4. 复审通过进入「试运营」，试运营期建议 30 至 90 天，期间设备接入量与在线率达标方可转正式。
  5. 正式入驻后厂家可自助创建子账号、导入设备台账、建立绑定关系。

审核要点清单：

审核维度具体材料判定标准
主体资质营业执照、生产许可、行业资质真实有效，经营范围覆盖申请品类
产品能力产品型号清单、技术参数、通信协议文档协议可对接，指标定义清晰
售后能力服务网点、工程师配置、备件库存覆盖销售区域，有备件保障能力
商务条件服务范围、SLA 承诺、结算方式承诺的服务水平可考核

2.3　角色体系与权限矩阵

平台采用「租户 + 角色 + 数据范围」三层权限模型。角色定义在各租户内，同一角色在不同租户下的权限含义一致，但数据范围不同。

平台运营侧角色：

角色核心职责数据范围
平台超级管理员系统配置、租户管理、权限分配全局
入驻审核员厂家入驻资质与技术审核全局入驻数据
运营专员租户日常管理、工单跟踪、争议仲裁全局业务数据
数据运营统计报表、指标口径管理全局脱敏数据

厂家端角色：

角色核心职责数据范围
厂家管理员子账号管理、设备台账导入、绑定关系审批本厂家全部数据
售后工程师工单接单与处理、告警处置本厂家数据
厂家查看者只读查看本厂家数据

客户端角色：

角色核心职责数据范围
客户管理员子账号管理、设备验收、工单验收本租户全部数据
厨房操作员日常巡检、报修发起、告警确认本租户数据
客户查看者只读查看本租户数据

2.4　数据可见范围与权限隔离

绑定关系是权限判定的唯一依据，分为两类且缺一不可：

绑定类型代码含义建立方式用途
装配绑定ASSEMBLY部件装在设备上（物联网传感器 → 厨具设备）厂家自行申报 + 平台校验支撑多方数据汇聚到同一设备
产权绑定OWNERSHIP设备交付给客户（设备 → 客户租户）厂家申报 + 客户确认 / 平台核验支撑客户资产视图与权限隔离

可见范围规则：

角色可见内容不可见内容
厨具厂家自产设备的台账、绑定到这些设备的客户信息、整机运行状态与告警、由这些设备产生的工单同行业其他客户的任何信息、非本厂设备的台账、客户合同与财务数据
物联网厂家自产部件的台账与固件状态、部件所采集的指标数据、部件附着设备的运行摘要、由部件触发的告警厨具本体的型号参数与成本、客户敏感信息、客户的经营数据
客户端本租户名下全部设备（含跨厂家的）、监控数据、告警、报修工单其他客户的任何数据、厂家内部成本与流程数据、其他厂家工单
平台运营方全量数据—（财务与合同字段按需脱敏，操作全程留痕）

隔离实现要点：

  1. 查询层强制注入租户条件：所有业务查询接口必须携带当前登录人的租户标识，服务端强制拼接数据范围过滤条件，不依赖前端传参。
  2. 绑定关系驱动可见性：厂家查询设备时，条件为「设备存在指向本厂的有效装配绑定或产权绑定」，而非「设备的产品型号归属本厂」——因为同一型号可能有部分在别人客户处。
  3. 跨厂家数据的中间层隔离：一台设备的数据由多个厂家贡献，各厂家只能读取自己贡献的部分字段，聚合视图由服务端组装后下发，不做前端拼接。
  4. 越权访问阻断：用户尝试访问无绑定关系的资源时，服务端返回资源不存在而非无权限，避免通过响应差异探测资源存在性。
  5. 操作留痕：租户管理员的账号管理、绑定关系变更、数据导出三类操作全部记入审计日志，含操作人、时间、变更前后值。

2.5　租户上下文与数据权限落地机制

平台的权限判定统一走「租户上下文」：

  1. 用户登录后，鉴权服务返回该用户所属租户、角色、以及数据范围表达式（如「本厂家全部」「本租户全部」）。
  2. 每次业务请求携带该上下文，服务端据此构造数据过滤条件。
  3. 绑定关系表作为权限判定的事实来源，任何权限判断都不硬编码具体客户或区域。

4.3　设备与客户绑定关系

绑定关系管理是厂家端区别于普通设备台账系统的核心功能。

绑定关系列表：

字段说明
设备 SN绑定主体设备
客户绑定的客户端租户
绑定类型装配绑定 / 产权绑定
绑定来源厂家申报 / 平台导入 / 客户确认
生效时间绑定关系开始生效的时间
当前状态待确认 / 生效中 / 待解除 / 已解除
操作人发起绑定的操作人

绑定流程：

  1. 厂家在设备列表中选择目标设备，发起绑定申报，指定客户租户与绑定类型。
  2. 系统校验：该设备当前是否已有生效中的同类型绑定；该客户是否在服务范围内。
  3. 绑定关系进入「待确认」，推送客户侧待办。
  4. 客户确认后绑定生效，设备进入该客户的资产视图；若客户在约定时限内未确认（如 7 天），绑定自动生效并记录为「厂家申报 + 超时自动确认」。
  5. 客户如有异议可拒绝并填写原因，绑定回到厂家侧待处理。
变更与留痕：绑定关系的建立、解除、转移均为 append-only 记录，每次变更生成新版本记录，保留变更人、变更时间、变更原因。历史绑定关系永久可查，用于追溯设备归属变更历史。

6.2　工单状态机

状态状态码状态含义操作方

处理中IN_PROGRESS厂家已接单，正在处理厂家

流转规则：

流转触发条件触发方附带要求
待接单 → 处理中厂家接单厂家填写接单说明、预计到场时间
处理中 → 待验收厂家反馈处理结果厂家填写处理过程、更换备件、上传现场照片
待验收 → 已完成客户验收通过客户可填写满意度评价
待验收 → 处理中客户验收驳回客户必须填写驳回原因
已完成 → 已关闭归档客户或系统已完成满 7 天自动归档
待接单 → 已关闭客户撤单客户仅在厂家接单前允许，需填写撤单原因

状态机约束：

  1. 状态不可跳跃，任何状态只能按上表定义的路径流转。
  2. 验收驳回必须填写原因，驳回后回到「处理中」，工单返回次数需记录，超过 3 次需平台介入。
  3. 工单一旦进入「已关闭」不可再变更，仅可查看。
  4. 每次流转生成一条不可修改的流转记录，含操作人、时间、动作、备注。

6.3　客户报修流程

1. 客户从设备列表或告警详情点击「发起报修」
2. 系统自动带入设备信息、关联告警、责任厂家
3. 客户选择问题类型、填写问题描述、上传现场图片、选择优先级
4. 提交 → 工单进入「待接单」，SLA 计时开始
5. 推送通知给责任厂家的厂家管理员与售后工程师
6. 客户可在工单列表跟踪进度

设计要点：报修入口必须在设备上下文与告警上下文中都可直达，客户无需先找到设备再找报修按钮。

6.4　厂家处理流程

1. 厂家工作台收到工单待办，查看设备台账与历史告警
2. 接单 → 填写接单说明与预计到场时间，工单进入「处理中」
3. 厂家执行维修，可多次更新处理进展
4. 处理完成 → 填写处理过程说明，登记备件更换，上传现场照片
5. 反馈 → 工单进入「待验收」，推送客户验收待办

备件更换记录：作为工单的子结构独立记录，每条记录包含备件名称、规格、数量、SN、是否旧件回收、旧件去向。备件更换记录在工单完成后仍需保留，作为质量追溯与质保责任依据。

处理进展更新：厂家可在处理中多次更新进展，更新记录含时间、进展说明、附件。进展更新是超时判定的重要依据，长时间无更新的工单进入超时预警。

6.5　验收与关闭

1. 客户收到待验收通知，查看处理说明与备件记录、现场照片
2. 验收通过 → 工单「已完成」，可填写满意度评价
3. 验收驳回 → 必须填写驳回原因，工单退回「处理中」
4. 已完成满 7 天自动归档 → 工单「已关闭」
5. 归档后工单只读，作为履约记录与数据来源

验收环节是平台履约质量的把关点，驳回机制保证客户对服务结果的最终认可权。

6.6　超时提醒与升级

SLA 时限按优先级与厂家承诺共同确定，超时处理分三级升级。

SLA 时限基准：

优先级接单时限处理时限待验收时限
紧急30 分钟4 小时24 小时
高2 小时8 小时48 小时
中8 小时24 小时72 小时
低24 小时72 小时7 天

超时升级机制：

升级级别触发条件动作
一级提醒达到 SLA 时限的 80%站内信提醒厂家处理人
二级催办超过 SLA 时限站内信 + 短信，同时通知厂家管理员
三级升级超过 SLA 时限 200%平台运营介入，工单标记争议，厂家 SLA 计入考核
待验收超时的特殊处理：客户侧超时不应计入厂家违约。系统在待验收时限到达时仅提醒客户，若客户持续不确认，超过 7 天后工单自动转为「已完成」并归档，同时记录「客户未确认」标记，不计入厂家履约考核。

统计口径：平台按季度统计各厂家的按时接单率、按时处理率、验收通过率、平均响应时长，形成厂家服务能力画像。

第七章　各角色操作流程

7.1　厂家入驻流程

厂家注册 → 创建入驻申请 → 填写主体资质与产品能力 → 提交
    → 平台初审（资质核验）
    → 平台复审（技术对接 + 商务确认）
    → 试运营（30-90 天，接入设备验证能力）
    → 正式入驻 → 开厂家伙账号与设备台账功能

7.2　设备接入与绑定流程

厂家导入设备台账 → 平台校验通过
    → 申报装配绑定（部件 → 设备）
    → 申报产权绑定（设备 → 客户）
    → 客户确认（超时自动确认）
    → 绑定生效，设备进入客户资产视图
    → 设备数据上报，进入监控与告警

7.3　告警到工单的转化流程

设备数据异常 → 规则引擎判定触发 → 生成告警记录
    → 推送厂家与客户
    → 厂家确认告警，判断是否需要现场处理
    → 需要 → 厂家主动发起工单
    → 或客户查看告警后主动发起工单（自动关联告警）
    → 工单流转 → 告警状态随工单进度更新为「处理中」

7.4　工单全生命周期

客户发起 → [待接单] → 厂家接单 → [处理中] → 厂家反馈 → [待验收]
    → 客户验收通过 → [已完成] → 自动归档 → [已关闭]
    → 或客户验收驳回 → 回退至 [处理中]

第八章　相比原有逻辑的改动点

8.1　改动点总览

序号改动点原有问题调整后影响范围
1平台定位展示工具，无商业闭环双边交易与履约基础设施全局
2租户模型无租户概念，数据全局可见引入租户作为隔离基本单位全部业务模块
3设备台账仅聚合计数，无个体档案设备 SN 级个体台账数据模型
4物联网部件未作为独立对象建模部件作为独立台账，附着于设备数据模型
5绑定关系无装配绑定 + 产权绑定双类型权限、工单、数据汇聚
6角色体系无角色区分三方共 10 类角色 + 数据范围权限模块
7权限隔离无隔离四类角色的可见范围规则全部查询接口

10审核流程无入驻管理七状态入驻审核新增模块
11组织模型地产式「集团-省域-网格-宗地」租户式「厂家租户 / 客户租户」组织架构
12通知机制无站内信 + 短信 + 邮件多通道新增模块

8.2　关键改动说明

改动点 5（绑定关系）是最重要的结构性改动。原设计中厂家只是「设备来源」标签，没有「谁把设备卖给了谁」的概念。双边平台必须回答厂家的核心诉求——「我的设备在谁手上、跑得怎么样」，这只能通过绑定关系回答。同时，绑定关系也是权限隔离的依据：厂家对某客户可见，当且仅当该客户持有该厂家的某台设备。

改动点 11（组织模型）需要特别注意。原系统使用的「集团-省域公司-网格-宗地」是地产行业模型，在双边平台中不再适用。取而代之的是租户模型，层级从「空间归属」变为「法人归属」。原有组织树相关逻辑需要废弃重建，不能简单映射。

改动点 2（租户）是最基础的前置改动。所有数据表都需要增加租户标识，所有查询都需要注入数据范围条件，这是影响面最广的一项。建议在数据模型设计阶段一次性到位，避免后续反复改造。

9.2　关键依赖链

平台存在三条不可逆的依赖链，必须按序建设：

  1. 租户权限 → 绑定关系 → 全部业务模块：绑定关系是权限判定的事实来源，没有绑定关系就无法实现数据隔离，也无法确定工单责任方。
  2. 设备台账 → 绑定关系 → 告警中心 → 工单引擎：没有设备就没有告警，没有告警就没有工单触发源，工单闭环无法起点。
  3. 工单引擎 → 通知服务 → 超时提醒：超时提醒依赖定时任务与通知通道，两者缺一则 SLA 形同虚设。

9.3　建议建设顺序

阶段建设内容交付标志

第二阶段设备台账、绑定关系服务厂家可导入设备并申报绑定，客户可见本方设备
第三阶段告警规则引擎、告警中心、监控数据设备监控与告警可查可处置
