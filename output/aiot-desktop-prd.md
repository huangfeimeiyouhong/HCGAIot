## 0. 已有资产盘点与工程决策（先回答两个问题）

### 0.1 结论：新建独立工程，不复用 iot-cockpit 仓库，但复用其组件与令牌

| 维度 | iot-cockpit 现状 | 新建独立工程的理由 |
| --- | --- | --- |
| 主题 | 深色科技风（`#061230` 底、`html/body overflow:hidden`、全局隐藏滚动条） | 桌面管理后台需要浅色 + 页面级滚动，全局样式直接冲突，改动会污染大屏 |
| 适配方式 | `self-adaption` 按 1920×1080 整屏缩放 | 桌面端需 1440~2560 自适应流式布局，缩放壳逻辑不适用 |
| 交付形态 | 单页大屏 + `standalone/*.html` 单文件（已构建产物在 `dist/`） | 大屏是独立交付物，独立工程边界更清晰，不影响已有成果 |
| git 状态 | 已有完整提交历史与构建产物 | 新目录零风险，不引入回归 |

**建议落地方式**：新目录 `/Users/phil/WorkBuddy/后厨管家AIoT平台/iot-desktop/`，`package.json` 复制 iot-cockpit 的依赖版本（保证 npm 缓存命中、`node_modules` 可直接软链复用），组件按下方清单**复制**而非引用。

备选方案（不推荐）：在 iot-cockpit 内开 `desktop/` 子目录 + 双主题变量切换。可行但需同时维护 `cockpit-dark` / `admin-light` 两套 SCSS 分支，且必须改动全局 `index.scss`，回归风险高于收益。

### 0.2 可直接复用 / 需改造 / 不复用

| 分类 | 资产 | 用途 |
| --- | --- | --- |
| **直接复制复用**（~15 个） | `base-chart`（ECharts 封装）、`gauge-chart`、`pagination`、`select`、`date-picker`、`cascader`、`tree`、`tree-select`、`section-tab`、`nav-tab`、`num-with-unit`、`name-value-item`、`base-svg-icon`、`loading`、`no-image-placeholder` | 图表与通用控件；三入口共用同一套 |
| **需改造复用** | `data-table`（配置列驱动，浅色下需调边框/表头）、`dialog`（大屏样式需改浅色）、`panel-card`（改为浅色卡片） | 表格与弹窗是后台主力，改造量集中在 SCSS |
| **不复用** | `self-adaption`（整屏缩放）、`border-box-13`（赛博边框）、`liquid-chart`、`pie-3d-*`、`video-player`（大屏专用） | 与后台场景无关 |
| **mock 层参考** | `src/views/iot-cockpit/data.ts` 的「生成器 + 轻微抖动」写法、`src/api/iot.ts` 的 `delay()` 模拟网络延迟模式 | 新工程照此写 `src/mock/*`，页面层仍走 `api` 调用，**为将来接后端留零改动切换口** |
| **登录页背景** | `standalone/china.geo.js` + `template.html` 地图下钻写法 | 复用为**登录页**的深色科技风背景（唯一保留深色的场景），延续品牌感 |

### 0.3 大屏的归属决策

说明书 3.1 / 8.3 要求保留「平台总览大屏」。**本阶段不纳入桌面端工程**：

- 大屏需要 `self-adaption` 缩放壳 + 深色主题，与后台浅色体系互斥；
- 已有 `iot-cockpit` 即为大屏资产，可独立交付；
- 桌面端平台后台仅保留一个**外链入口**（`/platform/screen`，打开已有大屏），并在 PRD 标注其为 P2。

## 1. 产品目标与成功判定

### 1.1 目标

| # | 目标 | 说明 |
| --- | --- | --- |
| G1 | 三入口结构完整 | 说明书第二～五章的每个功能模块都能在原型中找到对应页面，无遗漏、无自行发挥 |
| G2 | 数据隔离可被看见 | 三入口看到的 mock 数据严格符合说明书 2.4 可见范围规则，页面上有可见的数据范围标识 |
| G3 | 四条主链路可点通 | 入驻审核、绑定确认、工单闭环、告警转单四条链路各能完整走通一次状态流转 |

### 1.2 本阶段成功判定标准（可勾选）

- [ ] 入口选择页 → 登录 → 三端工作台，路径 ≤ 2 次点击可达
- [ ] 厂家入驻申请 7 状态（说明书 2.2）在列表与详情中均可看到，其中至少 1 条走完「待初审 → 待复审 → 试运营 → 正式入驻」
- [ ] 1 台设备走完「厂家导入台账 → 申报产权绑定 → 客户确认 → 绑定生效 → 设备出现在客户资产视图」
- [ ] 1 张工单走完「待接单 → 处理中 → 待验收 → 已完成 → 已关闭」，且备件记录、驳回原因、SLA 计时均可见
- [ ] 客户 A 页面无法看到客户 B 的任何设备/工单；厂家 A 页面无法看到厂家 B 的设备
- [ ] 平台方账号能看到全量数据，但财务/合同字段为脱敏展示
- [ ] 三入口在配色、间距、表格、弹窗、状态徽标上视觉一致（同屏截图可并排对比）

### 1.3 非目标（明确不做）

移动端、真实登录鉴权、真实数据持久化、跨端数据写入联动（**同一 mock 实体在A 端流转后，B 端数据不自动变化，仅静态呈现最终态**）、大屏重建、图表高级下钻。

> 关于最后一条：本阶段是静态原型，工单在厂家端点「接单」后，客户工单列表**以 mock 最终态展示**（体现为处理中），而非真正联动。原型中需在页面标注该约定，避免评审误解。

## 2. 信息架构与页面清单（可直接转路由表）

### 2.1 全局路由骨架

```
/                        入口选择页（三入口 + 演示说明）
/login                   登录页（?role=platform|vendor|customer）
/demo/guide              演示导览页（列出四条主链路 + 一键跳转按钮）  P1
/demo/isolation          数据隔离演示页（对照表：三角色可见范围）   P1

/platform/**             平台方后台（登录后落地 /platform/dashboard）
/vendor/**               厂家端    （登录后落地 /vendor/onboarding 或 /vendor/dashboard）
/customer/**             客户端    （登录后落地 /customer/dashboard）
/vendor/onboarding       入驻申请（**未入驻亦可访问**，厂家注册入口）
```

角色区分方式：三入口**共用登录页组件**，以 `?role=` 决定文案、演示账号下拉、登录后跳转目标；登录后角色与租户写入 Pinia `authStore`，菜单、可见数据、按钮权限均由该store 驱动。**角色二级区分**（平台 4 类/ 厂家 3 类 / 客户 3 类，见说明书 2.3）以登录页的「演示账号切换器」实现，不做完整账号体系。

## 3. 三入口统一设计体系

### 3.1 主题判断：后台主体用浅色，登录页保留深色

**结论**：桌面端管理后台采用**浅色主题**；仅**登录页/入口选择页**使用深色科技风（复用大屏地图资产）。

理由：

| 维度 | 浅色（推荐） | 深色 |
| --- | --- | --- |
| 信息密度 | 同屏可承载更多表格行与列，文本对比度更舒适 | 高对比炫光文本长时间阅读易疲劳 |
| 表格可读性 | 密集数字、SN、日期在浅底上更易扫读（管理后台 90% 场景是看表） | 深底浅字对长列表不友好 |
| 组件复用 | Element Plus 默认浅色，改造量最小 | 需逐组件覆写，深色表格/弹窗成本高 |
| 与大屏区隔 | 后台与大屏视觉明确区分，\"大屏=展示、后台=作业\" | 三入口全深色，与大屏混同 |
| 品牌延续 | 通过主色 `#41C0FF` 与登录页深色延续品牌 | 品牌感强但牺牲作业效率 |

## 4. 核心流程的静态交互设计（用户故事 + 验收标准）

> 通用约定：所有状态变更均为**当前页面 mock 数据的内存更新**，刷新后回到初始态；涉及跨入口的联动以「目标页展示最终态」体现，并在页面标注。

### 4.1 厂家入驻申请 → 平台审核

**用户故事**
- US-01作为厂家管理员，我要创建入驻申请并分步填写资质，以便平台审核我的准入资格。
- US-02 作为平台入驻审核员，我要按四维度要点逐项核验并给出结论，以便把不合格的厂家挡在门外。
- US-03 作为平台审核员，我要在复审阶段区分「资料问题」与「能力问题」，以便分别进入整改或驳回。
- US-04 作为厂家，我要看到我的申请当前卡在哪一步、被驳回的原因，以便快速补齐材料。

**验收标准**

| 步骤 | 页面 / 路由 | 操作 | 页面上必须能看到 |
| --- | --- | --- | --- |
| 1 | `/login?role=vendor` | 选厂家类型（厨具/物联网）→ 填账号密码登录 | 演示账号下拉含 4 个厂家身份 |
| 2 | `/vendor/onboarding` | 点击「创建入驻申请」 | 表单分 4 步：主体资质→ 产品能力 → 售后能力 → 商务条件 |
| 3 | `/vendor/onboarding` | 填完点「提交审核」 | 状态徽标 `DRAFT`→`PENDING_PRIMARY`（待初审）；进入该状态后**关键字段置灰不可编辑** |
| 4 | `/login?role=platform` | 切平台账号登录 → 入驻申请列表 | 列表出现该申请，状态「待初审」，可筛选到 |
| 5 | `/platform/review/applications/:id` | 点击「通过初审」 | 状态 → `PENDING_SECONDARY`（待复审）；时间轴追加记录（操作人/时间/意见） |
| 6 | 同上 | 填技术对接信息（协议、字段映射）+ 商务确认（SLA 承诺） | 技术/商务信息区块可填写并保存 |
| 7 | 同上 | 选「资料问题 → 标记整改」并填原因 | 状态 → `RECTIFY`（待整改）；原因在时间轴与详情可见 |
| 8 | `/vendor/onboarding` | 厂家侧查看 | 显示整改原因 + 「提交整改材料」按钮 |
| 9 | `/platform/review/applications/:id` | 再次复审 → 「通过复审」 | 状态 → `TRIAL`（试运营），提示试运营期 30~90 天 |
| 10 | 同上 | 在租户管理中确认转正 | 状态 → `ACTIVE`（正式入驻）；`/vendor/accounts` 与 `/vendor/models` 菜单随之解锁 |

**额外必须覆盖的驳回分支**：复审选择「能力问题 → 驳回」→ `REJECTED`，厂家侧显示「重新发起申请」按钮。
**验收口径**：7 个状态（DRAFT / PENDING_PRIMARY / PENDING_SECONDARY / RECTIFY / REJECTED / TRIAL / ACTIVE）在列表筛选与详情时间轴中均可见，且 mock 数据中每状态至少 1 条。

### 4.2 设备台账 → 绑定申报 → 客户确认

**用户故事**
- US-05 作为厂家管理员，我要批量导入设备台账并看到失败行原因，以便快速修正。
